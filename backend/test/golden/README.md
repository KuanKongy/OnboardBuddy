# Golden explanation fixtures

`npm run explain` scores generated PROSE the way `npm run truth` scores
deterministic extraction. Same idea, different half of the pipeline:
`truth-diff.ts` asks "did the parser find the right routes?", `explanation-diff.ts`
asks "is the text an explanation of THIS repo, or of a repo-shaped thing?".

## Why five shapes

The reviewer's note was *"test your features versus various projects since some
of your features or prompts may not generalize well"*. One repo cannot show
over-fitting. These five were chosen so a prompt tuned to any one of them
visibly breaks on another:

| fixture | shape | what it stresses |
| --- | --- | --- |
| `masterpokedex` | Vite + React SPA, react-router, no server | pure client app: no routes, no queues, no schema — the CONSULT sections have nothing to tabulate |
| `skribbl` | SPA **plus** a plain-JS Express + Socket.IO server | mixed TS/JS, and an interaction surface made of socket events rather than HTTP routes |
| `floowforge` | Next.js App Router + a **Python** FastAPI backend | honest coverage: ~40 route handlers no parser can read. Silence about them reads as "this repo has no backend" |
| `onboardbuddy` | TS monorepo (this repo) | the only fixture with a schema, a queue, a worker and a real journey graph — the shape every prompt was written against |
| `p-limit` | 5-file published library | few or no detectable entrypoints. No pages, no routes, no jobs, no clusters. Every section must degrade gracefully instead of inventing structure |

`p-limit` belongs to a third party, so the product cannot analyse it (no GitHub
App installation) — its prose row always reports SKIP. That is the point of
including it: the harness must be loud about what it did not score, and the
deterministic half still proves the shape is what the fixture claims.

## Scored on properties, not text

No fixture contains expected prose. Each declares what must be TRUE of any
acceptable explanation:

- **domain nouns** — the repo's own vocabulary appears (a Skribbl package that
  never says "room" is about some other program)
- **receipts** — claim paragraphs carry evidence
- **disclosure** — `mustDisclose` names things the analysis could not read;
  the package has to admit them
- **no screen narration** — zero error-severity findings from `explanationLint.ts`
- **cluster altitude** — each `## <cluster>` subsection is about that cluster

## The ratchets

`budgets` are **today's measured debt**, not aspirations. The gate fails when a
number gets worse, which is how you introduce a quality gate against prose that
has never had one. Lower them as the generator improves; never raise them
without saying why in the fixture.

Re-measure with `npm run explain -- --repos <dir>`; the `measured:` line is
printed for every scored repo on every run, so no budget is a magic number.

## First measurement — 2026-07-25

Four packages generated by the same pipeline, same prompts, same model, within
one hour of each other.

| repo | domain nouns | claims cited | narration errors | altitude errors | sections naming a gap |
| --- | --- | --- | --- | --- | --- |
| **OnboardBuddy** (home field) | 7/8 | 55.6% | **21** | 3 | **2/12** |
| Skribbl | 8/8 | 64.2% | 31 | 4 | 5/12 |
| MasterPokedex | 7/8 | 42.9% | 30 | 6 | 6/12 |
| **FloowForge** | 8/8 | 45.1% | **53** | 3 | 4/12 |

Read across the rows, not down them — the spread is the generalization signal.
Three things stand out:

1. **FloowForge fails `P3 disclosure`, and it is left red on purpose.** 100 of
   its 167 files are the Python FastAPI backend. Not one ORIENT or UNDERSTAND
   section says the word "Python". A new joiner reads the package and concludes
   FloowForge is a frontend. Every other budget in these fixtures is today's
   measured number; this one is a requirement, so it stays failing.
2. **Narration errors scale with distance from home field**: 21 on the repo the
   prompts were written against, ~30 on the two small apps, 53 on the monorepo.
   31 of FloowForge's 53 are leaked internal keys
   (`wf:web/app/p/[token]/page.tsx:PublicFormPage`, `cluster:web/modules`) in the
   capabilities section. `sectionSpecs.ts` forbids exactly this — the
   instruction held on small repos and broke on the monorepo. That is what a
   prompt failing to generalize looks like, measured.
3. **The home-field repo discloses the least.** 2 of 12 sections admit any
   limit, against 6 of 12 on MasterPokedex. Confidence is highest where the
   prompts fit best, which is the opposite of what you want.
